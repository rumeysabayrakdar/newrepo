01 Purpose & product boundary

Recreate the lightweight Arçelik App Store catalogue and external-link redirect site. V1 includes the two catalogue tabs, search, categories, detail screenshots/documents, admin management, translations and user/admin event logs. No binary hosting, installation, post-MVP reporting or dashboards. Backend: C#/.NET; frontend: React.

MVP only. No V2 Reports or V3 Dashboards are planned. Future versions are optional post-MVP enhancements, not implementation commitments.

02 Audiences, roles & identity

Roles are Employee/User and Admin only; no Super Admin or Approver. An existing Admin can grant or revoke Admin access for an existing employee identity. The site cannot create employee master records. Production uses Okta; Test uses a clearly labeled fake login. Missing required identity context produces an error.

03 Test personas & switching

Create a demo persona per role, e.g. Zeynep-Admin and Rümeysa-Employee (synthetic examples). Test users can switch personas easily without restarting the site; switching must update visible menus, permissions, country and employee-type targeting. Add further synthetic employee variants only to test eligibility combinations. No Test personas or fake login in Production.

04 Employee journey & responsive experience

Sign in → choose Arçelik-developed or Other tab → search/filter by category → open application details → see description, version, screenshots, documents and all eligible download/open links → follow a configured URL. Desktop starts with a responsive card grid and uses a list plus half-page detail pane while browsing; mobile uses a single-column list and full-screen detail with download options near the top. Do not hide assigned links based on device.

Implementation priority: make the user journey functional with a simple, usable React interface first. Desktop split-detail, visual refinements, animation and pixel-perfect mockup alignment are design-stage refinements after core workflows are verified. Basic mobile usability and access to all links remain MVP requirements.

05 Catalogue & targeting

Applications may target multiple countries, employee types, platforms and categories. Empty country selection means Global. Apply country/Global and employee-type eligibility on the server; the semantics of empty employee-type/platform assignments and link-specific country fallback require confirmation. Category filters must support applications assigned to multiple categories. Inactive or archived items are not displayed in the employee catalogue, subject to confirmed archival behavior.

06 Admin experience & preview

Admins can create and edit applications, categories, versions, public links, screenshots, user documents, translations and targeting, and manage active/archived state. Countries and categories use searchable multi-select dropdowns with checkboxes. On mobile use a searchable full-screen or bottom-sheet selector with Apply/Cancel and a selected-item count. The editor provides a live private preview of unsaved changes. Preview alone never changes the public catalogue; Save publishes validated changes immediately. No approval or draft-approval process.

Prioritize working Admin CRUD, eligibility configuration, private preview, save, and audit before visual polish. Multi-select country/category controls must be usable; advanced visual styling can follow functional validation.

07 Admin access & archive

An Admin can add another existing employee as Admin by their employee identity; this is an access assignment, not employee creation. Record grants and revocations. There is no Super Admin. Preserve archived items using an explicit Boolean isArchived field, without deleting their records or historical logs. Keep isActive distinct unless the business confirms otherwise.

08 Links, documents & logging

Show all user-eligible assigned links regardless of current device, including country-appropriate links. Validate the stored URL and recheck eligibility before redirect. Each download/open click and each search action creates a separate ActionLog record, even when repeated by the same user. Every admin create/edit/active/archive/role change creates a separate AdminAuditLog record identifying actor, time, action and affected record. A click does not prove installation. Define exact search-trigger and redirect failure policy before implementation.

09 Errors, access & security

Show clear errors for missing claims, expired sessions, ineligible/archived applications, invalid links, unavailable documents, save conflicts and server failures. Protect direct endpoints with server-side authorization; never rely on hiding React menus. Restrict audit access and avoid storing secrets in logs. Include correlation IDs for support.

10 Environments & technology

No Norm dependency. Development is performed collaboratively by Rümeysa and ChatGPT using a locally run C#/.NET backend and React frontend, with deployment hosting/repository/database decisions left open. ChatGPT can prepare and revise source code, tests, configuration templates, documentation and troubleshooting instructions; local execution, credentials, infrastructure access and production deployment require user-controlled tools and access.

11 Scope & acceptance

MVP delivery prioritizes functioning backend, database, authentication, catalogue, admin, targeting, links, translations and append-only logs. Minimal functional React screens precede detailed responsive design refinements. No post-MVP reporting or dashboards are included.

Functional acceptance still covers both catalogue tabs, search/categories, application details, images and documents, eligible links, translations, Admin CRUD and role assignment, private preview and immediate save, Boolean archiving, separate user/admin event logs, eligibility, and Test/Production isolation. Detailed UI polish follows successful functional testing.

12 Open decisions

Confirm .NET/React versions, database, local tooling, hosting and repository; Production inventory and targeting/link semantics; Okta claim names and first Admin bootstrap; archive and inactive rules; search event trigger; URL policy and redirect logging failure behavior; languages/fallback, document/image storage, audit retention/access and backup/rollback ownership. Do not assume answers.

13 Optional post-MVP ideas (not committed)

V2 is a placeholder for enhancements evaluated after MVP completion, not a reporting/dashboard roadmap.

Candidate enhancements to discuss later: integrating an additional service; retrieving images from an app store; fetching external-source data; optionally filtering application links by the user’s current device.

Further recommendations for later review: automated link health checks, improved content-management ergonomics, and richer audit exploration. Each requires explicit approval before adding scope.
